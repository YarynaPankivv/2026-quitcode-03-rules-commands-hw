# Перевірка (Task B, C і бонус E)

## Task B — чи бачить інструмент AGENTS.md

- **Інструмент:** Claude Code (desktop app, модель Opus 5 / Sonnet 5)
- **Як перевірила:** два прогони в **нових** сесіях — до і після виправлення
  `CLAUDE.md`. У кожному прохання: перелічити правила проєкту з контексту, **не
  відкриваючи файлів**. Плюс `/context`, розділ **Memory files**.

### До виправлення — посилання не працює

У `CLAUDE.md` було markdown-посилання `[AGENTS.md](./AGENTS.md)`. Нова сесія
перелічила лише вміст `.claude/rules/do-not-touch.md` (правило без frontmatter,
тому завантажується завжди), а про базу написала дослівно:

> «Також є посилання на AGENTS.md як джерело загальних конвенцій проєкту
> (сам файл я не відкривав).»

Тобто агент бачив **рядок тексту**, а не вміст: жодної команди (`npm test`,
`check:rules`), жодного пункту з карти проєкту він назвати не міг. Це і є різниця
між посиланням та імпортом.

Побічно та сама сесія підтвердила Task A: `architecture` і `conventions` у списку
не з'явилися — вони прив'язані до `paths: app/src/**/*.ts`, а файлів застосунку
в контексті не було.

### Після виправлення — імпорт `@AGENTS.md`

У `CLAUDE.md` тепер окремий рядок `@AGENTS.md`.

`/context` → розділ **Memory files** (2.4k, 3 файли):

```

  E:\Homework\Homework3\CLAUDE.md                241
  E:\Homework\Homework3\AGENTS.md                1.2k

```

`AGENTS.md` (1.2k) — окремий запис у Memory files, хоча сам файл ніхто не
відкривав: його підтягнув рядок `@AGENTS.md` із `CLAUDE.md`. Поруч видно
`do-not-touch.md` (975) — правило без frontmatter, яке завантажується завжди.
`architecture.md` і `conventions.md` у списку відсутні: вони прив'язані до
`paths: app/src/**/*.ts` і в цій сесії не потрібні.

Нова сесія, прохання назвати команди й захищені теки без відкриття файлів —
агент відтворив таблицю команд із `AGENTS.md` разом із базовою лінією:

> **Команди проєкту.** Усі виконуються з теки `app/`: `npm install` —
> встановлення (лише devDependencies); `npm test` — Vitest, разовий прогін;
> `npm run typecheck` — `tsc --noEmit`; `npm run check:rules` — статична
> перевірка конвенцій проєкту.
> Базова лінія на чистому репо: **18 тестів зелені**, `check:rules` →
> `TOTAL: 8 violation(s)` (спадковий код у `sheets-append.ts` і `sync/state.ts`).
> Перед комітом обов'язково: `cd app && npm test && npm run typecheck && npm run check:rules`

Числа в цитаті — стан `AGENTS.md` на момент прогону (Task B). Після Task C
спадковий код переписано, і тепер там стоять актуальні числа поточного стану;
для доказу завантаження це значення не має ваги — важливо, що агент назвав вміст,
якого не бачив до виправлення `CLAUDE.md`.

І далі — захищені теки з `do-not-touch.md`: `app/src/core/**`, `app/scripts/**`,
`materials/**`, `.coderabbit.yaml`, `.github/**`, разом із протоколом зупинки
(«зупинитись, описати потрібну зміну в `core/` та чекати підтвердження людини»)
і забороною перегенеровувати `core.lock.json`.

**Результат: база завантажується.** Команд і базової лінії немає в жодному
правилі — це вміст виключно `AGENTS.md`, і саме його агент не міг назвати до
виправлення.

Умови двох прогонів: той самий репозиторій (між ними змінено лише `CLAUDE.md`),
те саме прохання, обидва — нові сесії Claude Code на Sonnet 5. Строгого контролю
за недетермінованістю моделі тут немає, тому коректне формулювання таке:
**спостережена різниця узгоджується з ефектом імпорту `@AGENTS.md`** і
підкріплена прямим доказом — рядком `AGENTS.md` у Memory files виводу `/context`,
який не залежить від формулювань моделі.

### `/analyze-error`

- **Виклик:** `/analyze-error materials/error-log.txt`
- **Чи підставився `$ARGUMENTS`:** так. Команда відкрилась із рядком
  **«Ціль: materials/error-log.txt»** — Claude Code підставив текст після назви
  команди в плейсхолдер, запасне пояснення в шаблоні не знадобилось.
- **Тригер:** `ENOSPC: no space left on device` о 00:05:00 — нічний бекап забив
  диск до 100%, `saveState` впав на `writeFileSync`
  (`app/src/sync/state.ts:21`, стек через `runSync` → `app/src/sync/run.ts:18`).
- **Корінна причина:** `app/src/sync/state.ts:11–18`, функція `loadState` —
  **тихий фолбек на початковий стан**. `JSON.parse` у рядку 14 кидає виняток на
  пошкодженому файлі, `catch` у рядках 15–17 повертає
  `{ lastSyncedAt: "1970-01-01T00:00:00.000Z" }` і **не лишає жодного сліду в
  журналі**. Після цього кожен лід новіший за 1970 рік, тобто «непрочитаними»
  стають усі ліди за всю історію — звідси ld_0001 о 00:15 і далі.
- **Механізм:** `writeFileSync` відкриває файл на запис і **обрізає його до нуля
  перед записом**, тому падіння по ENOSPC лишило `data/sync-state.json`
  порожнім. О 00:13:48 диск звільнили — тригер зник, — але о 00:15:00 `loadState`
  прочитав уже зіпсований файл і мовчки повернув 1970.
- **Чому проблема пережила зникнення тригера (9 годин):** цикл замикають два
  рядки. `app/src/sync/run.ts:18` — `saveState(statePath, state)` **безумовно**
  записує щойно прочитаний стан назад, тобто підмінене 1970 стає валідним JSON
  на диску: пошкодження «загоюється» в стійко хибну позначку, і з цього моменту
  `JSON.parse` більше не падає. А єдине місце, де позначка рухається вперед, —
  `app/src/sync/run.ts:36`, у **кінці** прогону; але прогін щоразу розсилає
  півтисячі лідів на три інтеграції, впирається в 429 з повторами й отримує
  `SIGKILL` на ліміті 4m30s (рядки логу 00:19:30, 00:24:30 і далі) — до рядка 36
  виконання не доходить ніколи. Кожні 5 хвилин: прочитати 1970 → записати 1970 →
  розіслати все заново → бути вбитим → повторити.
- **Порушена конвенція:** `.claude/rules/conventions.md`, пункт про зовнішній
  текст: «Невалідний JSON або несподівана форма — це `{ ok: false, error }`…
  не підставляй "значення за замовчуванням" і не продовжуй роботу мовчки — так
  пошкоджені дані стають непомітними». `npm run check:rules` показує це як
  `src/sync/state.ts  json-via-parse  line 14` — єдине порушення, що лишилось у
  проєкті.
- **Підсилювачі (не причина):** неатомарний запис у `state.ts:21` (temp-файл +
  `rename` зберіг би попередній стан); безумовний `saveState` на старті
  `run.ts:18`; просування позначки лише в кінці прогону (`run.ts:36`) замість
  чекпойнта по ходу; відсутність guard на форму стану — навіть валідний JSON
  іншої форми пройде без помилки.
- **Запропонований тест (не написаний):** `app/src/sync/state.test.ts`,
  випадок «`loadState` не підставляє початковий стан для пошкодженого файлу»:
  записати у тимчасовий файл обрізаний JSON (`{"lastSyncedAt":`), викликати
  `loadState` і ствердити, що результат — помилка, а не `1970-01-01`. Сьогодні
  падає. Другий випадок у `run.test.ts`: із пошкодженим файлом стану `runSync`
  не має розсилати вже доставлені ліди.
- **Чи зупинився там, де сказано в Stop:** так. На момент звіту жодного файлу не
  змінено — ні `state.ts`, ні тест; `check:rules` показував `TOTAL: 1`.
  Виправлення зроблено **окремим кроком, після підтвердження людини**.
- **Виправлення (після підтвердження):**
  - `loadState` повертає `Result<SyncState>` і розбирає файл через
    `parseJson(text, isSyncState)` — пошкоджений файл або несподівана форма тепер
    помилка, а не мовчазне `1970-01-01`.
  - `saveState` пише в `<path>.tmp` і робить `renameSync` — заповнений диск валить
    запис тимчасового файлу, а поточний стан лишається цілим.
  - З `run.ts` прибрано безумовний `saveState(statePath, state)` на старті, який
    закріплював хибну позначку на диску; при помилці читання стану `runSync`
    пише `log.error` і повертає порожній звіт, нічого не розсилаючи.
- **Тести, що відтворюють проблему:** новий `app/src/sync/state.test.ts` (5
  випадків) і випадок «не розсилає нічого, якщо файл стану пошкоджений» у
  `run.test.ts`. Перевірено, що вони справді ловлять інцидент: із поверненим
  старим кодом `npx vitest run src/sync` дає **6 із 8 тестів червоними**, з
  виправленням — усі зелені.
- **Числа після виправлення:** `npm test` **34 зелених**, `npm run typecheck`
  чисто, `npm run check:rules` → **`TOTAL: 0 violation(s)`** (зникло останнє
  порушення `json-via-parse` у `src/sync/state.ts:14`). Це стан на момент
  виправлення інциденту; після правок за рев'ю CodeRabbit тестів **40**.
- **Спостереження про саму команду:** корінну причину знайдено з першого разу
  завдяки кроку 3 («чому проблема тривала після того, як тригер зник?»). Без
  цього кроку природна відповідь зупиняється на ENOSPC — диск справді
  закінчився, стек справді вказує на `saveState`, і все сходиться. Питання про
  дев'ять годин після 00:13:48 — єдине, що змушує піти далі.

  > сам `log.ts`. … зміна в `core/` має йти окремим PR через рев'ю платформної
  > команди — підтвердіть, і я опишу конкретний diff для того PR, але не коммічу
  > в `core/` сам.»

  Тобто захист має два шари й вони спрацьовують по черзі: **правило** зупиняє
  агента, який його прочитав, а **хук** ловить того, хто правил не бачив або
  вирішив їх обійти — саме такий випадок і показала спроба `Edit` вище.

- **Що виправлено після зовнішнього рев'ю скрипта:**
  - Порівняння шляху було через `includes()`, тож будь-який шлях із підрядком
    `materials/` блокувався хибно (рядок 3 таблиці). Перша спроба виправлення —
    ручне відрізання кореня через `startsWith` — закрила хибне спрацювання, але
    лишила дірку: запис `./app/src/core/log.ts` проходив повз захист, бо рядок
    починався з `./`. Тепер шлях зводиться до відносного через
    `path.relative(cwd, path.resolve(cwd, filePath))`, тож `./`, `..` і
    відмінності регістру на Windows нормалізуються до одного вигляду.
  - Додано matcher `Bash`. Спершу він закривав лише `--write-lock`, і рев'ю
    CodeRabbit слушно вказало, що `printf x > app/src/core/types.ts` проходить
    повз захист. Тепер команда ріжеться на сегменти по `&&`, `||`, `;`, `|`, і
    сегмент, що згадує захищений шлях, дозволяється лише за **переліком
    дозволеного** — читання (`cat`, `grep`, `git diff`, `git log`) і відновлення
    (`git checkout --`, `git restore`). Перелік саме дозволеного, а не
    забороненого: способів записати файл з оболонки (`>`, `sed -i`, `tee`, `rm`,
    `dd`, `cp`) наперед не перелічити, а пропустити хоч один означає зняти захист.
    Зворотні слеші нормалізуються, тому `echo hi > app\src\core\http.ts` теж
    блокується.
- **Знайдено й виправлено під час перевірки:** перша версія скрипта при
  нерозпізнаному вхідному JSON виходила з кодом `0`, тобто **мовчки пропускала**
  дію. Для захисту це хибна стратегія: варто форматові входу змінитись — і
  блокування зникає непомітно. Тепер нерозібраний вхід дає код `2` з поясненням:
  гучна відмова видно одразу, мовчазну дірку — ні.
