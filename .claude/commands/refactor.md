# refactor

**Ціль:** $ARGUMENTS
(Якщо в рядку вище немає конкретного файлу — ціль вказана в повідомленні одразу
після назви команди. Немає й там — спитай і зупинись.)

## Кроки

1. **Зафіксуй базу до роботи** і випиши числа:
   ```bash
   cd app && npm test && npm run check:rules
   ```
   З розділу `by file` візьми кількість порушень саме для цільового файлу.
2. Прочитай цільовий файл і його тест `<модуль>.test.ts`. Те, що стверджують
   наявні асерти — URL, тіло запиту, тексти помилок, порядок викликів — це
   **контракт**. Він не змінюється.
3. Приведи файл до `.claude/rules/conventions.md` і `.claude/rules/architecture.md`.
   Кожне порушення зі звіту `check:rules` має зникнути заміною на відповідний
   експорт ядра, а не приглушенням перевірки.
4. Збережи зовнішню поведінку дослівно: той самий URL із тими самими параметрами,
   те саме тіло запиту, ті самі рядки помилок. Якщо конвенція вимагає іншого
   формату повідомлення в журналі — це допустимо лише там, де тест цього не
   стверджує.
5. Прогони ті самі перевірки ще раз і порівняй числа з кроком 1.

## Acceptance criteria

- [ ] `check:rules` для цього файлу: було `N` → стало `0`; загальний `TOTAL` зменшився рівно на `N`
- [ ] `cd app && npm test` зелений, кількість тестів не зменшилась
- [ ] `git diff -- <тест цільового файлу>` не містить змінених асертів (лише додані, якщо додавав)
- [ ] URL, тіло запиту й тексти помилок ті самі, що до рефакторингу
- [ ] `git status --short` не містить шляхів із `.claude/rules/do-not-touch.md`

## Stop

Чіпай лише вказаний файл. Якщо для приведення до конвенцій потрібна зміна іншого
модуля, ядра або асертів у тестах — зупинись, покажи, що саме заважає, і чекай
підтвердження. Якщо після змін хоч один тест червоний — не «підправляй» тест:
повертай поведінку коду.
